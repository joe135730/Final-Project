Che-Yi   Wu,   Yu-Hsuan   Yang       1 ⃣   Overview   ●   Build   a   distributed   real-time   traffic-monitoring   system   simulating   smart-city   infrastructure.     ●   Many   sensor   nodes   generate   continuous   data   ( road ,   vehicle_count ,   avg_speed ).     ●   Data   is   sharded   and   replicated   across   multiple   servers   for   scalability   and   fault   tolerance.     ●   A   map-style   dashboard   displays   each   road’s   live   status:     🔴   Congested  🟡   Moderate  🟢   Smooth.     ●   Demonstrates   partitioning   (hash   sharding) ,   replication ,   consistency ,   and   failure   recovery .       2 ⃣   Goals   ●   Continuously   collect   and   update   traffic   data.     ●   Distribute   load   across   servers   using   hash   sharding .     ●   Maintain   consistent   replicated   data   during   failures.     ●   Keep   end-to-end   latency   <   1   s   from   sensor   →   dashboard.     ●   Show   quantitative   metrics   proving   scalability   and   fault   tolerance.             3 ⃣   Detailed   Design   ●   Sensor   Nodes     ○   Simulate   intersections   or   vehicles;   send   JSON   {road,timestamp,vehicle_count,avg_speed}   via   HTTP   POST   /ingest .     ○   Randomly   change   roads   to   mimic   vehicles   moving.     ●   Server   Cluster   (3   nodes)     ○   Hash   sharding:   shard_id   =   hash(road)   %   P   (   P   ≈   6   ).     ○   Each   shard   has   1   leader   +   1   follower   (   replication   factor   2   ).     ○   Round-robin   placement   →   balanced   load   across   srv-1/2/3.     ○   Leader   handles   writes   &   replicates   to   follower;   followers   can   serve   reads.     ●   Replication   Layer     ○   Lightweight   Raft-style:   heartbeats,   append   entries,   majority   commit,   leader   election   on   timeout.     ●   Dashboard   UI     ○   Web   map   (e.g.,   HTML   +   Chart.js   or   Streamlit)   polls   /summary   every   few   hundred   ms.     ○   Colors   roads   green/yellow/red   based   on   latest   average   speed   and   vehicle   count.     ●   Data   Storage     ○   In-memory   aggregates   +   optional   JSON   snapshot   for   persistence.       4 ⃣   Assumptions   ●   Failures:   Crash-stop;   one   server   failure   at   a   time.     ●   Network:   Reliable   TCP;   minor   delay   tolerated.     ●   Workload:   10–200   sensors,   1–5   updates/s.     ●   Cluster:   3   servers,   6   shards,   replication   factor   2.     ●   Users:   Dashboard   viewers   and
